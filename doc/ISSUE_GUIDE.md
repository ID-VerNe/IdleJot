# 怎么发 Issue（Issue 操作指引）

> 本文件是仓库内所有 Agent 的 issue 操作规范，**必须遵照执行**。
> 配套：怎么开 PR 见 [PR_GUIDE.md](PR_GUIDE.md)；流程总览见 [AGENTS.md](../AGENTS.md) §2.7。

## 定位：issue 是最小执行单元

- 一个 issue = 一件可以独立交给一个会话（或一个 agent）、独立验收、独立关闭的事。
- **只开 issue 不动手修**：巡检/值守时遇到问题（不分大小）先提 issue；修不修、谁修、什么时候修，由 issue 的讨论决定。**主水群 Agent 的产出止于 issue**（AGENTS.md §0，issue #160）：不派 subagent 代劳，执行交给用户启动的独立会话。
- 不开 issue 就动手 = 无据可查。任何「我觉得这里有问题」都必须先变成带证据的 issue。

## 什么时候开

| 场景 | type | label |
|---|---|---|
| 功能坏了、行为不符合预期 | `bug` | `bug` |
| 门禁/测试自身有缺陷（误报、漏报、环境依赖） | `bug` 或 `fix` | `bug` |
| 新功能/新能力需求 | `feat` | `enhancement` |
| 清理死代码/死脚本、CI 配置等杂务 | `chore` | 视内容定 |
| 重构（不改外部行为） | `refactor` | 视内容定 |
| 测试体系增补 | `test` | 视内容定 |
| 文档新增/修订（含操作指引、实机验证回填） | `docs` | `documentation` |
| 协作规范/流程约定（Agent 行为边界等） | `[规范]` | `documentation` |
| 对照某存档报告的缺口总账 | `[追踪]` | `enhancement` |
| 合并态快照、落地汇总、实机验证结果 | `[记录]` | `documentation` |
| 可行性/调研报告，作为后续 issue 的引用源头 | `[存档]` | `documentation` |
| 审计发现（泄露、缺陷复核） | `Audit` | `bug` |

早期 issue（#1–#55 时代）有的没带前缀（如 #22、#55），**新开 issue 一律带前缀**。

## 标题规范

```
type(scope): 一句话摘要
```

- 摘要说清「什么坏了 / 要什么」，扫列表即读懂项目状态，不写「有个问题」。
- `scope` 标注子系统（`水群` / `ci` / `测试` / `审计` / `数据` / `agents` / `water-group`…），可省略。
- 同根因关联互相引用编号：第二代修复标题带第一代编号（#89 标题含 `#79 第二例`）。
- 真实示例：

| 标题 | 要点 |
|---|---|
| `bug(ci): check_mcp_chat_turns 的 needs_wait 断言撞 1 秒窗口，慢机器上抛 KeyError`（#106） | 说清门禁名 + 触发条件 + 症状 |
| `[规范] 水群主 Agent 不再派 subagent 干其他活，只立 issue 不排执行`（#160） | 规范类用方括号类型，正文即规范 |
| `bug(水群): 追问额度扣到 0 仍会唤醒一次并报「额度还剩 0 条」，窗口下一轮才收`（#98） | 精确到错误文案，可 grep 复现 |
| `[存档] Miao-Yunzai 接入水群机器人 — 可行性与风险报告`（#2） | 存档类标题即报告主题 |
| `[追踪] 对照 #2 附录 A：米游社接口落地缺口盘点（已接入 14 / 未接入 18）`（#42） | 追踪类带被对照物 + 量化结论 |
| `Audit: personalized personal information leaked across slim branch`（#76） | 审计类直接说暴露面 |

## 正文四要素（缺一不可）

### 1. 现象

行为类 issue 的现象段必须交付**一条可直接粘贴进 PowerShell 的复现命令**，外加它的期望输出、实际输出与触发条件——没有命令的现象无法验收，只能退回补充：

| 字段 | 要求 |
|---|---|
| 复现命令 | 一条，能整段粘贴执行（带 `.venv/Scripts/python.exe` 前缀与必要参数）；跨多步的先归并成单行命令或一个可整段粘贴的代码块 |
| 期望输出 | 正常时应当看到什么（原文或关键行） |
| 实际输出 | 现在看到什么，贴**原文**（含 retcode、错误文案） |
| 触发条件 / 频率 | 什么环境、什么条件下触发；偶发给出「出现次数 / 总次数」，必现直接写必现 |

- 非行为类 issue（纯文档、纯重构、纯规范）在现象段写 `复现命令：无（不涉及运行时行为）` 即可。
- 好例：#98 贴出「额度还剩 0 条」原文与唤醒时序；#97 贴出 `app.log` 双倍横幅。
- 反例：「有时候会失败」「感觉不太对」——无法复现的一律退回补充，先贴 `needs-repro`（见下节）。

### 2. 证据链

- 每一条判断都要有 `文件:行号` 或可复现命令；日志给出路径与关键行。
- **无证据不修复**（AGENTS.md §2.6）：没有证据的 finding 视为虚构，曾因子代理整段虚构目录与常量返工。
- 好例：#41 逐条列出「自述 vs 实际」核对结果；#91 给出 `run_hidden` 吞输出的调用点。

### 3. 影响面

- 谁受影响（哪个群/哪条链路/哪个门禁）、什么条件下触发、严重度用**优先级 `P+数字`**：P0 阻断 / P1 常见 / P2 边角。
- 修复顺序按优先级在 issue 里定，不在实施时定（#53 的 P0/P1/P2 即现行优先级标识）。
- 一件事装不下的大 issue：先定**分节（`P+字母`）**再拆分——一个分节 = 一个可独立合并的 PR，命名规则见 [PR_GUIDE.md](PR_GUIDE.md)「拆分与命名规范」。

### 4. 修复候选 + 回归建议

- 给出建议方向（不要求完美方案），并明确**用什么门禁/测试钉住复发**。
- 每个被修的缺陷都应留下「墓碑」：门禁脚本 + 注释写明防哪个 issue 复发（如 `check_path_hygiene.py` 防 #14 复发）。

## 复现命令与 `needs-repro`

发 issue 时给不出可粘贴的复现命令，就贴 `needs-repro` 标签，不要硬写「有时候会」：

- **发现者**：补上一行命令与期望/实际输出后摘标签；确实补不出来，就在 issue 里说清为什么不可复现（时序、外部服务、权限），由维护者判断是否降级为观察项。
- **修复者**：写 plan 时必须先回填一行验收基线——`用 issue 的复现命令复现：成功 / 失败（贴原始输出）`。**复现失败（命令跑不出症状）说明 issue 描述与现状不符，退回发现者补充，不进实施**；复现成功才摘 `needs-repro` 开始改。
- **回签**：合并后用同一条命令再跑一次，流程见「关闭：行为类靠回签，不靠合并」。

## 发布前过隐私门禁（硬要求）

标题和正文写好后，**先过发布门禁再发**——issue 一发出去就永久留在 GitHub 上，真实 QQ / 群号 / 花名一旦带上就是泄露：

```bash
# 草稿先落文件（标题也放进去，标题同样扫）
.venv/Scripts/python.exe scripts/check_publication.py --require-private --text issue-draft.md
gh issue create --title "<标题>" --body-file issue-draft.md
```

门禁从私有库（`~/.water-group`）**实时派生**真实号码与花名，仓库里不写死任何名单；通用词例外放私有 `publication_allow.txt`。同一个门禁也跑 commit message（`commit-msg` 钩子）和 push（`pre-push` 钩子），规则见 [AGENTS.md](../AGENTS.md) §5.3。

## 关闭：行为类靠回签，不靠合并

issue 的关闭点跟着「验收」走，不跟着「合并」走：

- 纯文档 / 纯重构 PR 可以 `Closes #NN`，合并即关闭。
- 行为类 PR（`fix` / `feat` / `perf`，以及任何改运行时代码的 PR）正文用 `Refs #NN`；合并后 issue 保持打开并贴 `needs-live-verify`，等回签。
- **回签**由发现者（或全新上下文的验证 agent）执行，按 [PR_GUIDE.md](PR_GUIDE.md)「合并后：对账与回签」的模板贴复现命令、实际输出与实机证据；结论为「症状消失」才摘标签并关闭，仍复现则摘标签留 issue 并补证据。修复者不能给自己回签。
- 发现者的职责不止提供原始日志：修复结果必须回到 issue 里，被同一条复现命令验一遍。

## 记录三件套（用 issue 做项目记忆）

| 类型 | 用途 | 范例 |
|---|---|---|
| `[记录]` | 合并态快照：某阶段落地汇总 + 实机验证结果，后续 issue 的现状基准 | #7 水群 `#` 指令体系落地汇总 |
| `[存档]` | 可行性/调研报告：结论与风险清单，被后续 issue 引用为源头 | #2 Miao-Yunzai 接入可行性报告（#42 即对照它的附录 A） |
| `[追踪]` | 缺口总账：逐项列「已做 / 未做 / **评估后建议不做并终结**」，防止同一缺口被反复重开 | #42 米游社接口落地缺口盘点 |

实机验证结果不写进 issue 长文，用 docs PR 回填仓库文档，issue 里只留结论与链接。

## 反模式

- 一个 issue 塞多件事——无法独立关闭，拆成多个：按分节（`P+字母`）定步骤、按优先级（`P+数字`）定顺序，命名规则见 [PR_GUIDE.md](PR_GUIDE.md)「拆分与命名规范」。
- 只有结论没有证据——按 §2.6 退回。
- 把 issue 当聊天记录/进度播报——过程写 PR 评论，结论写 issue。
- 修完直接推主干——必须走 PR（见 [PR_GUIDE.md](PR_GUIDE.md)）。
- 行为类 issue 用 `Closes` 合并即关——症状没被复现命令验过，关闭只是修复者的自述。
- 现象只写「有时候会失败」、没有可粘贴的命令——先贴 `needs-repro`，补齐后才进实施。

## 模板（可直接抄）

```markdown
## 现象

- 复现命令：`<一条可直接粘贴进 PowerShell 的命令>`
- 期望输出：<正常时应看到什么>
- 实际输出：<现在看到什么，贴原文>
- 触发条件 / 频率：<环境 / 条件 / 偶发或必现；非行为类写「无（不涉及运行时行为）」>

## 证据链

- `<文件>:<行号>`：<该处代码/配置说明了什么>
- 日志：<路径> 关键行 <...>

## 影响面

<谁受影响、什么条件、严重度 P0/P1/P2>

## 修复候选

<建议方向；用什么门禁/测试钉住复发>
```
